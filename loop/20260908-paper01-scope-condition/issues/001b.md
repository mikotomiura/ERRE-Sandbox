### mutation testing (AC 001b-MUT)

11 mutant を機械的に列挙 (enum 値の潰し・順序破壊 / dataclass フィールド欠落・型変更 /
`frozen=True→False` / docstring 所有者差し戻し / anchor 欠落・順序破壊 /
`collect_preregistration()` のキー欠落)。各 mutant で
`assert old in s` → `assert new != old` → 書込み → `assert new in on_disk` → verify 実行 →
復元 → **復元後の byte 一致を SHA-256 で assert**、を自動化したハーネスで実施
(スクリプトは `feedback_witness_needs_mutation_testing` の規律どおり)。

**結果: 11/11 KILLED、生存 0**。詳細ログ:
`experiments/20260908-paper01-scope-condition/results/mutation-log-I001b.md`。

**issue 本文が名指しした核心 mutant** (`"INCONCLUSIVE"` を `"DEFLATION_REJECTED"` に写す、
ログの M1) は含まれており、個別に確認した: 4 test
(`test_config_matches_preregistration` / `test_config_mismatch_is_detected` /
`test_stage1_outcome_enum_is_frozen` / `test_inconclusive_is_not_rejection`) が
**同時に KILL** する。特に AC 001b-4 専用の `test_inconclusive_is_not_rejection` は
`mod.STAGE1_OUTCOME_ENUM` から値を読んで `Stage1Result` を構築する構造のため、この mutant
適用下では `inconclusive.stage1_outcome == rejected.stage1_outcome`
(両方とも `"DEFLATION_REJECTED"` に潰れる) となり
`assert inconclusive.stage1_outcome != rejected.stage1_outcome` で落ちる
— 「判定不能が棄却に潰れたら test が落ちる」の直接証拠。

**ツール側の学び**: mutation ハーネスの最初の実行で「復元したのに byte 不一致」という
false failure を踏んだ。原因はこのファイルが Windows で一貫して CRLF (595/595 行) であるのに、
`pathlib.Path.write_text()` のデフォルト universal-newline 変換に頼って `\n` 空間で
mutate→書込み→復元の往復をしたこと。改行コードが往復で正規化されて元の byte 列と
食い違った。修正: 読込時に `\r\n → \n` を明示変換してマッチングし、書込み時に
`\n → \r\n` を明示変換した raw bytes で書く方式に変更し、以後は正しく動作した
(詳細はログ冒頭に記載)。

**mutation 後の意味突き合わせ**: 再生成した `config.json` を実読みし、
design-final.md §9 (frozen pre-registration table) と新規 `stage1_outcome_enum` を
1 対 1 で突き合わせた。既存 10 キーの値は無変更 (diff は `stage1_outcome_enum` の 5 行追加のみ)。
